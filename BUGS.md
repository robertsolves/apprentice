# apprentice — bug audit

## Field reports

Filed by `apprentice bug` while working. Each has a suggested fix to review; none is applied.

### F1 · `approve <token> --text` with no words throws the proposal away — 2026-11-02
- Repro: a pending `type` proposal `7c2e`; run `apprentice approve 7c2e --text` with no replacement text after it.
- Cause: `Commands.approve` (`Sources/apprentice/Commands.swift:470-478`) calls `Approvals.take(token)` first, which drops the proposal from `pending.json`, and only then throws exit 5 for the empty text. The neighbouring branch for `--text` on a proposal that is not a `type` re-adds `p` ("Nothing was done, so the proposal stays pending"); this one does not, so the step the caller meant to approve is gone and the original command has to be run again for a new token.
- Suggested fix: `Approvals.add(p)` before that throw, as the non-`type` branch does, so `approve <token> --text "…"` or a plain `approve <token>` still works.

### F2 · `drag` keeps only the "may be irreversible" warning for the drop target — 2026-11-02
- Cause: `Commands.drag` (`Sources/apprentice/Commands.swift:1103`) and the VM's drag (`Sources/apprentice/Remote+More.swift:268`) pass `warn: Gate.warnings(dst, page).filter { $0.hasPrefix("may") }`. A destination inside a dialog, on a settings or billing page, on a credential field, or matching `[gate] user_only` loses those ⚠ lines: only `Gate.words` hits survive, so `Gate.forUser` warnings can never reach the proposal for the target. `gate()` already adds the source's own warnings.
- Suggested fix: pass the destination's warnings through unfiltered, as `upload` and `choose` do.

### F3 · `read` clears a challenge record on any page that has a password field — 2026-11-02
- Cause: `Challenge.find` (`Sources/apprentice/SiteRules.swift`) returns nil early when the page holds a password field, or a sign-in code marker on a site with `[login]` on. `Commands.read` (`Sources/apprentice/Commands.swift:693-696`; the VM's copy is `Remote.swift:531`) reads that nil as "the challenge is gone" and clears `Limits.challenged[domain]`, lifting the site's pause. A challenge that redirects to a sign-in page — the usual "confirm it's you" flow — is therefore cleared by the first `read`.
- Suggested fix: clear the record only when a check is conclusive. Keep the marker recorded when the challenge started and require that page to be gone, instead of treating `find` returning nil as proof.

### F4 · The cooldown check picks an arbitrary matching site — 2026-11-02
- Cause: `Cooldown.check` and `Cooldown.warning` (`Sources/apprentice/SiteRules.swift:317` and `:325`) use `l.cooling?.first(where: { Site.matches(domain, $0.key) })`. Dictionary order is unspecified and `Site.matches` is a suffix test, so when `example.com` and `sub.example.com` both have entries, the expired parent entry can be the one returned while the subdomain is still cooling — and `warning` can warn about a cooldown that has ended.
- Suggested fix: take the longest key that is still live, as `Budgets.cap` already does for sites: `l.cooling?.filter { $0.value.until > now && Site.matches(domain, $0.key) }.max { $0.key.count < $1.key.count }`.

### F5 · A flow's indented steps are silently skipped — 2026-11-02
- Cause: `Playbooks.steps` (`Sources/apprentice/Playbooks.swift:253`) accepts a line only when everything before its first "." is numeric. A step written with leading spaces before its number — `  1. click 5`, as Markdown lists usually are — fails that test and is dropped, so `do` runs fewer steps than the flow lists and still ends with `done`.
- Suggested fix: test the prefix of the trimmed line and drop the indentation with it; a step that cannot be parsed should be reported rather than skipped.

### F6 · A pipeline name with " #" in it is truncated when the file is read back — 2026-11-02
- Repro: `apprentice pipeline new "Budget #2 review" "first step"`, then `apprentice pipeline list`.
- Cause: `Pipelines.render` (`Sources/apprentice/Pipelines.swift`) writes front matter as `name: \(p.name)` with no quoting, and `Pipelines.parse` strips a trailing comment with `if let hash = value.range(of: " #") { value = String(value[..<hash.lowerBound]) }`. A name, agent or VM containing ` #` is cut at the space on every read: the pipeline lists as "Budget", and the next `pipeline add` rewrites the file with the short name, so the user's own title is lost for good.
- Suggested fix: quote the front-matter values as `Schedules.q` already does, and only treat ` #` as a comment when the value is unquoted. Either way, re-render what was read so a round trip is lossless.

### F7 · `project save --push` never records the repository it makes, so the next push fails — 2026-11-03
- Repro: a project with no `remote` in `projects.json`; `apprentice project save --push` makes the private repo and pushes; run `apprentice project save --push` again before the daemon's next sync round (or with `[sync] on = false`, at any time).
- Cause: `Projects.save` (`Sources/apprentice/Projects.swift`) decides by `p.remote`, and its `gh repo create … --push` branch never calls `Projects.setRemote`. The only caller of `setRemote` is `Sync` (`Sources/apprentice/Sync.swift:409`), which returns early on any project whose origin is not the signed-in account and does not run at all with sync off. The second `--push` therefore sees `remote == nil` again, takes the create branch, and `gh repo create --remote origin` fails because `origin` already exists: the command throws `could not make a GitHub repository: …` instead of pushing. `project list` also keeps showing no remote.
- Suggested fix: after a successful `gh repo create`, read the new URL and call `Projects.setRemote(dir, url)`; and in the `p.remote` lookup, fall back to `git remote get-url origin` so an existing origin is pushed to even when the entry has not been recorded yet.

### F8 · In the VM, an id from `ocr` can never be used: every action on it says stale — 2026-11-03
- Repro: a session in the Linux VM (`vm on`), `apprentice ocr`, then `apprentice click <id>` on one of its lines.
- Cause: OCR elements carry an empty `path` because they are not in the accessibility tree; on this Mac `resolve` (`Sources/apprentice/Reader.swift:309-310`) returns such an element as it is, so the caller clicks its box. The VM's `Remote.resolve` (`Sources/apprentice/Remote.swift:353-366`) has no such case: it looks for `$0.path == e.path && $0.key == e.key` in a fresh accessibility snapshot, which never contains an OCR line, then for a single element with that key, finds none, and throws `stale: element N changed, re-read`. Every VM command that resolves an id is affected — `click`, `type`, `hover`, `upload`, `download`, `scroll --in`, `drag` — so the only way to act on OCR text in the VM is `click --at x,y` from the listing.
- Suggested fix: add the Mac's early return to `Remote.resolve`: `if e.path.isEmpty { return e }` before the snapshot comparison.

### F9 · A settings choice with no choices crashes the window — 2026-11-03
- Repro: add `[setting.agent.effort]` with `kind = "choice"` and no `choices` line to `~/.apprentice/settings-screen.toml`, then open the window's Settings screen.
- Cause: `AppForms.swift:69` builds `kind = .choice(v["choices"].flatMap(Toml.array) ?? [])`, so a missing or empty list gives `.choice([])`. The row's control (`Sources/apprentice/AppUI.swift:1919`) binds the Picker with `choices.contains(value) ? value : choices[0]`, and subscripting an empty array traps: the window process dies (the daemon keeps running, since it is a separate process). Every other kind degrades instead — `number` falls back to `range.lowerBound`, `font` falls back to `AppLook.system` — so a half-written row in a file the user is invited to edit takes the whole screen down rather than showing nothing.
- Suggested fix: fall back to `choices.first ?? ""` in the binding, and skip a `.choice` setting with an empty list in `Settings.shown` (or read it as `.text`) so the row is left out. A `selftest` check that every shipped `[setting.*]` of kind choice carries at least one choice would catch the same mistake in `agent/settings-screen.toml`.

### F10 · The Sites screen shows the built-in value where a site inherits another's — 2026-11-03
- Repro: in the window's Sites screen pick "Every website", set "Actions a minute, at most" to 8, then open any other website (say `example.com`) that has no settings of its own. Its row reads 15, not 8, and is marked `usual`; the daemon runs it at 8. The same happens after `apprentice pace example.com fast`: the "Overall pace" row says Fast, while every timing below it still shows the steady numbers.
- Cause: `SiteSettings.usual` (`Sources/apprentice/SiteSettings.swift:195-207`) rebuilds what applies from scratch for `store = "pace"`: `PaceConfig.preset(builtInStyle(site, config: files.config), on: config.defaultPace).literal(field.key)`, and `builtInStyle` (`:211-220`) only knows three answers — `careful` for a social site, the style of a `[pace.styles]` list that names `web`, else `steady`. It never looks at the site's own entry in a `[pace.styles]` list, and never at `[pace.web]`, which is what the "Every website" row writes. The daemon resolves it differently: `Config.load` (`Sources/apprentice/Config.swift:605-620`) puts the steady preset in `profiles["web"]` and folds `[pace.web]`'s keys on top of it, and `profileKey` (`:702-711`) hands any site with no profile of its own to `profiles["web"]`. So the screen answers from the built-in preset while the daemon answers from `[pace.web]` (plus the site's listed style). Because the row shows `own ?? usual` (`Sources/apprentice/AppSites.swift:283`), the wrong number is not a greyed hint but the value the control displays, which is also what makes "Reset" look like it would change something it would not. Social sites are right: `profiles["instagram.com"]` is the careful preset with no `web` base under it.
- Suggested fix: answer `usual` from the profile the daemon would use instead of re-deriving a style — `config.profiles[site] ?? config.profiles["web"] ?? config.defaultPace` — and, when the site has a `[pace."<site>"]` section, rebuild that profile without `field.key` (the `PaceConfig(values, base:)` call `Config.load` already makes), so the value shown is the one that applies with this key absent. `builtInStyle` is still what `add` uses to pick a new site's starting style, so it stays; `usual` just stops needing it.
